הממצא האחרון משנה את המסקנה: שלב 3 עדיין לא הושלם.

מדיניות admin override של migration 20260809210000 נשארת תקפה לעריכת פעילות שכבר שובצה, אבל היא לא צריכה לעקוף validation של:

confirm-draft
final assignment
שמירת Draft חדש

יש להפריד בין שני המצבים:

1. עריכת פעילות קיימת

מנהל רשאי לערוך פעילות גם אם השינוי הופך את השיבוץ הקיים ללא תקין.

לכן:

העריכה לא נחסמת.
emp_id ו-instructor_name נשארים.
לאחר העריכה מתבצע revalidation.
אם השיבוץ כבר אינו תקין, instructor_assignment_status צריך להפוך ל-'נדרש טיפול'.

אין להחזיר את ה-validator הישן שחסם את עצם העריכה.

2. Draft / Confirm / Final Assignment

כאן ה-override לא חל.

לפני שמירת Draft, אישור Draft או שיבוץ סופי יש לבצע validation טרי מול הנתונים העדכניים.

אם מאז יצירת ה-Draft השתנו:

זמינות
חפיפה
זמן מעבר
מרחק
תאריכים
שעות
school_id
מפגשים

והשיבוץ כבר אינו תקין - אין לבצע את השיבוץ.

כלומר, confirm-draft לא יכול להיות authoritative אם ה-Draft כבר אינו תקין.

3. תקן את שורש הבעיה בלבד

בדוק בדיוק איזה RPC או helper עוקף כיום את scheduling_course_instructor_violations בגלל migration 20260809210000.

בצע את התיקון המינימלי כך ש:

manual post-edit override נשאר כפי שהוא
Draft/confirm/final assignment חוזרים להשתמש ב-validation הקנוני והטרי

אין לשנות ניקוד, matching, 40 ק"מ, 15 דקות, school_id, enforce_end_time או UI.

4. בדיקות חובה

הבדיקות מסוג SQL source inspection אינן מספיקות לבדן. יש להוסיף/להשתמש בבדיקת Postgres אמיתית שמריצה את ה-RPC בפועל ומוכיחה:

Draft תקין → זמינות משתנה → confirm-draft נדחה.
Draft תקין → נוסף שיבוץ מתנגש → confirm-draft נדחה.
שיבוץ סופי תקין → נשמר בהצלחה.
עריכת פעילות משובצת שהופכת את השיבוץ ללא תקין → העריכה נשמרת, השיבוץ לא נמחק, והסטטוס הופך ל-'נדרש טיפול'.

אם בדיקה 4 אינה אפשרית בגלל שהמנגנון הקיים כיום בכוונה מחזיר תמיד 'שובץ', תקן רק את post-edit revalidation כך שיחזיר 'נדרש טיפול' במקרה של כשל - בלי לחסום את העריכה.

לאחר מכן הרץ:

שמור Checkpoint חדש.

לא לבצע Push או Merge.
