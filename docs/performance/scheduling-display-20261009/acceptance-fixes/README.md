## 1. חסם הפרטים: סיבה ותיקון

ה־RPC הישן ביצע `FOR SHARE` על סביבת התכנון, ואז SELECT נפרד לפרטים. כאשר revision אינו מתאים הוא העלה `40001`, המיועד לכשל serialization אמיתי. PostgREST v14.17 משתמש ב־Hasql Transaction; זוהתה בספרייה של הבינארי המקומי הגרסה **1.1.0.1**. [המקור המדויק](https://github.com/nikita-volkov/hasql-transaction/blob/1.1.0.1/library/Hasql/Transaction/Private/Sessions.hs#L15) מפעיל `fix` / `Nothing -> retry` ומנתב `40001` ו־`40P01` לניסיון חוזר ללא מגבלת ניסיונות. אי־התאמת revision קבועה אינה משתנה בעקבות retry.

באבחון: SQL ישיר נכשל בתוך 0.82–2.78 ms ב־READ COMMITTED, REPEATABLE READ ו־SERIALIZABLE. ב־15 דגימות לא נמצאו ממתיני Lock או blockers. בקשת HTTP נקטעה אחרי 1,003.66 ms, ובכל זאת השרת המשיך לנסות; בלוג המבודד נספרו 34,139 שגיאות `planning_revision_conflict` עד עצירתו. לכן הכשל אינו המתנה לנעילה ואינו נפתר בהחלפת רמת בידוד. אין להריץ את השחזור הישן בייצור.

התיקון כולל שינוי מסלול הקריאה: הפונקציה `STABLE`, וקוראת revision ו־row_data **ב־SELECT אחד עם LEFT JOIN ובאותו snapshot MVCC**, בלי נעילת שורה. revision מיושן מחזיר `PT409` / HTTP 409 והודעת הדומיין הקיימת; אין retry של serialization. workspace חסר או revision חסר נדחים באותו מסלול. פרטים חסרים בגרסה נכונה עדיין מדווחים `planning_row_not_found`. בדיקת ההרשאה ו־grants לא השתנו.

בדיקת רגרסיה אמיתית דרך Data API: 10 בקשות לגרסה מיושנת החזירו 409 בתוך **3.50–37.06 ms**. ארבע בקשות נוספות בזמן writer לא־מחויב ולאחר commit הסתיימו בתוך **3.17–4.60 ms**: בזמן הכתיבה קוראים snapshot מחויב עקבי ללא המתנה; אחרי commit הגרסה הישנה נדחית והחדשה מצליחה. סף 1,000 ms הוא חסם בדיקת רגרסיה מבודדת, לא SLA ייצור. [לוג הרגרסיה](integration-results.txt), [אבחון](diagnosis.json).

## 2. SQL ו־JSON: מדידות לפני ואחרי

PostgreSQL 17.11, PostgREST 14.17, Supabase Auth 2.196.0. אותם 253 rows, אינדקסים מקוריים רלוונטיים ו־ANALYZE. חציון שבע דגימות לכל מסלול. זמן SQL: `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`; זמן HTTP נמדד בבקשה נפרדת עד קבלת כל הגוף. אין חיסור של מדדים מבקשות שונות. RPC אחד לכל דגימת טעינה. [לפני](final-before.json), [אחרי](final-after.json), [זהות fixture](fixture.json).

| מדד של display RPC | לפני התיקון | אחרי התיקון |
|---|---:|---:|
| SQL, כולל בדיקת הרשאה ומעטפת JSON | 182.971 ms | 136.264 ms (**−25.5%**) |
| הקרנה + helper תלויות + סריקת מערכים + jsonb_agg | 168.060 ms | 123.794 ms (**−26.3%**) |
| גוף תגובה בלתי דחוס | 1,658,878 bytes | 1,658,878 bytes |
| HTTP עד סוף הגוף, ללא parse | 199.216 ms | 161.729 ms (**−18.8%**) |
| JSON.parse בלבד | 5.564 ms | 5.946 ms |

מדידת בניית JSON אינה `jsonb_agg` טהור: היא כוללת סריקה, הקרנה, תלויות ותתי־שאילתות. אין שיפור מוכח ב־parse; התוכן והגודל זהים. RPC מלא קיים מחזיר 7,173,404 bytes באותו fixture; חסכון התעבורה המקורי נשמר. SQL החדש אינו בהכרח זול מ־RPC מלא בכל דגימה; מטרתו לשרת את התצוגה המצומצמת במהירות בלי להעביר חלופות שאינן פתוחות.

שורש העלות: גישות חוזרות למטען JSONB גדול המאוחסן ב־TOAST, לצד helper תלויות ומעברי מערכים. נוספה הרחבת payload פעם אחת לכל שורה (`LATERAL` עם גבול optimizer), ושורות מסודרות לפי activity_id **לפני** ההרחבה. ניסויי MATERIALIZED לכל סביבת התכנון או הרחבה לפני המיון יצרו כתיבה זמנית לדיסק ולכן לא נבחרו. בתוכנית הסופית Temp Read/Write = **0**; אין tuplestore ארצי חדש. תתי־השאילתות עדיין פועלות לפי שורה; האלגוריתם ונתוני התלות לא קוצצו.

השוואת deep equality עברה לכל 253 השורות וגם fixture קצה: מדריכים משותפים, נעילות, טיוטות, packing, substitutes ומפגשים חלופיים. גם סדרים וכפילויות קיימות נשמרו. פונקציית helper התלויות לא שונתה. display RPC סומן STABLE כדי שה־workspace, זהות העורך והשורות ייקראו באותו snapshot. [ראיות זהות התוצאות](parity.json).

## 3. עומס ומירוץ גרסאות

שמונה משתמשי מנהל שונים עם JWT אמיתי; אותה סביבה ואותם נתונים. מבחן בקצב מוצע זהה: 48 display ו־48 details לכל גרסה, כ־6 בקשות מכל סוג לשנייה, event loop נפרד לכל משתמש. כל הבקשות הושלמו. p95 מוגדר כדגימה באינדקס `floor(0.95*(n-1))` של הרשימה הממוינת. זהו מדגם בדיקה, לא התפלגות ייצור.

| HTTP תחת עומס זהה | לפני | אחרי |
|---|---:|---:|
| display: חציון / p95 | 274.5 / 547.8 ms | 174.8 / 229.9 ms |
| details: חציון / p95 | 11.4 / 27.4 ms | 7.5 / 14.9 ms |
| display: חציון זמן transaction מהשרת | 262.2 ms | 157.9 ms |
| details: חציון זמן transaction מהשרת | 5.35 ms | 2.05 ms |
| זיכרון anonymous מרבי שנדגם בקבוצת PostgreSQL | 115.92 MiB | 56.30 MiB |
| CPU מצטבר בחלון הדגימה | 11,175.6 ms | 8,171.6 ms |

זיכרון נדגם ב־cgroup, אינו peak RSS או זיכרון לדפדפן/בקשה. file cache נשאר 99.39 MiB. CPU כולל חלון בדיקה זהה בהיקפו ותהליכי שרת; אין להשליך יחס זה לכל סביבת ייצור. [דגימות בקצב זהה](offer-results.json).

בוצע גם מבחן closed-loop שבו כל משתמש מתחיל בקשה מיד אחרי קודמת: 1/4/8 משתמשים, 12/48/96 בקשות לכל גרסה. משך סבב 8 משתמשים ירד מ־7,494 ל־5,283 ms; display p95 ירד מ־1,686.5 ל־1,232.5 ms. details p95 באותו מבחן עלה מ־81.9 ל־94.1 ms אף שהחציון ירד מ־31.0 ל־17.2 ms. אין להסתיר זאת: קצב הגעת הבקשות והפרצים שונים בעקבות ההאצה, וגם לקוח המדידה המשותף מעבד תשובות JSON. במבחן הנפרד עם קצב הגעה קבוע ולקוחות עצמאיים העלייה לא שוחזרה. לא נמצאה נסיגה באותו עומס מוצע; עדיין קיימת שונות בזנב תחת עומס רווי.

מירוץ נוסף: 8 קוראים, 6 commits אטומיים ו־24 זוגות display/details. כל snapshots התצוגה היו עקביים; פרטים החזירו 22 קונפליקטים ו־2 תשובות עקביות, ללא שורה מעורבת בגרסה. פרטים הסתיימו לכל היותר בתוך 80.47 ms. [מדידות closed-loop ומירוץ](load-timed-results.json).

## 4. הרשאות, fallback וממשק בפועל

- 16 בדיקות הרשאות עברו: אדמין פעיל ומנהל מורשה ב־full/display/details ו־RLS; משתמש ללא הרשאה נדחה ב־403 ורואה אפס rows; הרשאת־בן בלי אב ואדמין לא פעיל נדחים; JWT משובש נדחה ב־401; anon חסום בשתי הפונקציות. משתמשים הונפקו ב־Auth, לא stub. [תוצאות](auth-results.json).
- שתי הפונקציות החדשות הוסרו **רק מהמסד המבודד** כדי לבדוק fallback. הלקוח המקורי עם Supabase JS בדפדפן מציג 253 שורות, פרטים מלאים וזהים, ודוחה revision ישן; ללא הרשאה אין עקיפה. stale נדחה בתוך 23.5–24.5 ms ב־fallback, וב־12–20.3 ms עם migration. 4 בקשות לסדרת display/details/full/stale עם migration, לעומת 9 ב־fallback. ה־migration הוחזר רק למסד המבודד. [תוצאות](module-results.json).
- כפתור Excel לא היה נגיש ברינדור המצב העדכני, אף שקיים handler. נוסף הכפתור הקיים למצב תכנון שמור ועדכני; הוא מוסתר ב־snapshot מיושן או בתכנון ממתין/לא תקין. נוסף revision guard מוגן RLS לאחר טעינת המקור המלא ולפני הורדה, גם אם כל השורות כבר hydrated, כדי לא לייצא קובץ ישן או מעורב בזמן writer. אין חישוב מנוע בעקבות ייצוא.
- נבדקו כניסה דרך מעטפת dashboard האמיתית, ניווט, חיפוש פעילות 252, פתיחת פרטים והורדת Excel **באמצעות הכפתור הטבעי**, ללא כפתור בדיקה מוזרק. שולחן עבודה 1440×900 ומובייל 390×844 עם האטת CPU פי 4. בשניהם נרנדרו לכל היותר 25 כרטיסים, והקובץ כלל את שלושת הגיליונות: 253 פעילויות, **759 חלופות**, **2,024 מפגשי מדריכים**. בוצע שינוי revision בין טעינת המקור לקבלת התשובה: בשני הפרופילים מוצג קונפליקט ולא נוצרת הורדה ישנה. אפס page errors ואפס בקשות כתיבה של היישום. [ראיות ממשק](ui-results.json).
- ארבעה משתמשי מנהל שונים הפעילו את הממשק במקביל: טעינת מסך, חיפוש, פרטים וייצוא מלא עברו. אין הרחבת הרשאות כדי לאפשר ניווט למסכים שאינם מורשים למנהל. [ראיות ארבעה משתמשים](ui-concurrent-results.json).

## 5. שימור נתונים ובדיקות אוטומטיות

בדיקת שימור נוספת עם **fixtures לא ריקים** עברה: תאריכים רשמיים, שיבוץ מאושר ונעול, טיוטת מדריך ומפגשים, אישורי ביצוע/נוכחות/שכר ושתי סביבות התכנון נשארו זהים לפני ואחרי תשע קריאות בשלושת התפקידים. hashes וספירות נשמרו. לא הופעלו מסלולי יצירה/ביטול אישורים, triggers או Storage חיצוני. [ראיות שימור](preservation.json).

בדיקות שנבחרו לפי שינוי והיקף קבלה: 4 מקרי integration כולל שלושת תרחישי HTTP/נעילה/commit; 2 מקרי כפתור ייצוא; 3 חוזי מצב/הפעלה קיימים; 13 מקרי תצוגה ומטמון (הקרנה, תלויות, 253 כרטיסים, quota/אחסון פגום, async cache, בחירה/גלילה, אי־החלת cache מיושן); 6 מקרי PWA/cache. כולן עברו. סבב המטמון הסופי הריץ את כל 13 המקרים (כולל 3 שכבר נבדקו בנפרד) במסגרת חזרה על בדיקות הקבלה לבקשת המשתמש; [לוג](cache-acceptance-tests.txt). הורצו עם `--test-isolation=none` כדי לוודא שמקרי `node:test` אכן מופעלים בתצורת המאגר, ולא להסתפק בסימון קובץ כ־pass. אין workflow E2E אוטומטי חדש. build נדרש לשינוי frontend והצליח (9.50 s); נשארו אזהרות bundle גדול. בדיקות Node מדווחות על יבוא CSS שאינו נתמך ב־Node, אך מקרי הבדיקה רצים ועוברים; דפדפן בפועל ללא שגיאות.

הרגרסיה הממוקדת החדשה: `tests/integration/scheduling-display-read-rpc.test.mjs`, manual בלבד. דורשת DB ו־Auth/API מקומיים על loopback, 253 רשומות בעלות מזהי `synthetic-`, workspace קבוע לפי fixture, ו־SESSION_FILE פרטי עם token אדמין. היא מסרבת ל־URL של מסד מתארח, ומחזירה את revision הסינתטי במנגנון finally. לדוגמה:

```sh
SCHEDULING_ACCEPTANCE_DB_URL=postgres://postgres@127.0.0.1:55441/postgres \
SCHEDULING_ACCEPTANCE_SESSION_FILE=/path/to/private-isolated-sessions.json \
node --test --test-isolation=none tests/integration/scheduling-display-read-rpc.test.mjs
```

נותרו: טעינה קרה כבדה ומובייל חלש; שונות בזנב תחת burst רווי; בדיקה על Supabase מתארח/גרסת runtime הייצור המדויקת ומובייל פיזי; תהליכי אישורים וכתיבות מחוץ להיקף PR1.
