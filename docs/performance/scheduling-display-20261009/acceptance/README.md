## סביבה והיקף

Supabase Auth אמיתי (`supabase/gotrue:v2.196.0`) ו־PostgREST (`v14.17`) מקומיים, מול PostgreSQL 17.11 זמני. משתמשים עם JWT חתום שהונפק ב־Auth; פונקציות `auth.uid`, `app_has_permission`, `app_permission_parent`, RPC ותנאי RLS המקוריים, ללא stub הרשאות. סכמות התכנון הועתקו מהמיפוי; במדידה הסופית הותקנו גם האינדקסים המקוריים הרלוונטיים ו־ANALYZE. כל 253 הרשומות הן אותו fixture סינתטי מהדוח הקודם. אין זו העתקה של כל סביבת הייצור: טריגרים ותהליכי כתיבה/Storage חיצוניים אינם כלולים. במערכת המחוברת אין branch פיתוח קיים, ולכן לא נעשתה בדיקה בענף Supabase מתארח. בייצור נקראו מטא־נתונים בלבד לצורך סכמות אישורים.

## מדידות נפרדות

חציון 7 דגימות לכל מסלול, באותו מסד ונתונים, ללא עומס מקביל יזום. RPC אחד לכל דגימה. זמן SQL באמצעות `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`, בנפרד מבקשת HTTP אחרת; לא מחסרים SQL מזמן HTTP כדי להמציא זמן רשת.

| מדד | RPC מלא קיים | RPC תצוגה חדש |
|---|---:|---:|
| SQL, כולל JSON בתוך הפונקציה | 129.777 ms | 190.306 ms |
| גודל גוף HTTP בלתי דחוס | 7,173,404 bytes | 1,658,878 bytes |
| HTTP עד קבלת כל הגוף, ללא parse | 213.942 ms | 207.459 ms |
| JSON.parse בלבד | 37.184 ms | 5.917 ms |
| HTTP+parse באותה דגימה, חציון | 279.819 ms | 213.376 ms |

שאילתת ההקרנה וה־jsonb_agg החדשה נמדדה ישירות, בנפרד מבדיקת הרשאה ומעטפת ה־RPC: **170.460 ms** חציון. המדד כולל סריקת השורות, הקרנת JSON, פונקציית תלויות והשאילתות הפנימיות — אינו מדידת `jsonb_agg` טהורה. תוכניות הביצוע נשמרו ב־indexed-measurements.json; תתי־השאילתות לאפשרויות ול־dependencySlots מבוצעים 253 פעמים. זמן ה־SQL החדש גבוה בכ־46.6%, מול הפחתת גוף תשובה בכ־76.9%. זו הוכחת עלות שרת נוספת; אין עדיין הוכחת שיפור בעומס מקביל. זמן טעינה כאן הוא בקשת נתונים מקומית, לא אתחול dashboard מלא. גדלי HTTP שונים מהדוח הקודם בשל סריאליזציית PostgREST ורשומת נעילה סינתטית.

## הכשל וצעדים נדרשים

`get_scheduling_planning_row_details` מעלה `planning_revision_conflict` עם SQLSTATE `40001`. התרחיש שוחזר שוב עם timeout של 4 שניות. באבחון מבוקר באותו מסד, החלפת הקוד בלבד ל־`P0001` החזירה HTTP 400 עם אותה הודעה בתוך **12.232 ms**. הגרסה המקורית שוחזרה לאחר האבחון. הממצא מבודד את התלות בקוד השגיאה, אך לא קובע שכל גרסאות PostgREST/סביבת הייצור מתנהגות כך; מנגנון הטיפול הפנימי ב־PostgREST לא נותח.

לפני המלצה חיובית למיזוג: לתקן קוד שגיאת קונפליקט ולבדוק שוב את מסלול Data API והלקוח; לצמצם/לבחון את עלות הקרנת JSON ולבדוק עומס מקביל; להשלים ניווט וכפתור Excel בתשתית dashboard מלאה. שימור אישורים בעת קריאה עבר, אך תהליכי אישור/ביטול ו־commit נותרו מחוץ להיקף בדיקה זו. לא מתחילים PR שני, ולא מפעילים migration בייצור ללא אישור נפרד.
