# חשבונות עסקה: טיוטות Outlook באמצעות Delegated

המסלול משתמש בחיבור Microsoft הקיים ב־`frontend/src/microsoft/graph-mail.js`.
אין בקשת הרשאות Application לדואר ואין קריאה ל־send או sendMail.
הרשאות SharePoint הקיימות משמשות לשמירת PDF בלבד ואינן משתנות.

## הפקה

1. שריון החשבון שומר בשרת את זהות המפיק וכתובתו הארגונית המאומתת.
2. הממשק מבקש טוקן בשקט מ־`delegatedMailToken`, עם אותה הרשאת `Mail.ReadWrite`
   שבה משתמשים תיאום הפעילויות וקליטת המדריכים. חוסר חיבור Microsoft אינו עוצר הפקת PDF.
3. `finance-transaction-accounts` מאמת הרשאת Supabase, נועל את החשבון, מפיק PDF,
   שומר אותו ב־SharePoint ומסיים את החיוב. בניסיון חוזר נעשה שימוש בקובץ המקורי וב־SHA-256 שלו.
4. השרת בודק שהמשתמש בבקשה הוא המפיק המקורי באמצעות `finance_delegated_account_owner`.
   טוקן Microsoft נשלח זמנית בכותרת `x-microsoft-mail-token`; אינו נשמר במסד, בתור או בלוג יזום.
5. Graph מאמת את הטוקן. השרת משווה את מזהה תיקיית Drafts ב־`/me/mailFolders/drafts`
   למזהה אותה תיקייה ב־`/users/{originalMailbox}/mailFolders/drafts`, עם אותו טוקן
   ואותן כותרות ImmutableId. ההשוואה חייבת להצליח לפני חיפוש או יצירת הודעה.
   כך חשבון שגוי, כולל חשבון שקיבל גישה משותפת לתיבת המפיק, אינו יכול ליצור טיוטה עבורו.
   אין הסתמכות על loginHint, פענוח טוקן בדפדפן או כתובת שהלקוח מספק. אין צורך ב־User.Read.
6. נמענים נשלפים מרשומות אנשי הקשר הפעילים ומשיוך המשלם בשרת.
   יצירת הטיוטה היא `POST /me/messages` עם כל הנמענים, נוסח אחיד וה־PDF כ־fileAttachment.
7. לפני הצלחה נבדקים isDraft, נמענים ו־hash הקובץ המצורף. נשמרים כתובת התיבה ומזהה הטיוטה.

אין שימוש ב־MS_MAIL_SENDER או בתיבה חלופית. כללי החיוב, הזכאות, שלושת מפגשי גפ״ן
ושורות המפגשים נשארים ללא שינוי.

## אבטחה והתאוששות

- נעילת ההפצה, כוונת היצירה, ImmutableId ו־FinanceAccountId נשמרים.
  תוצאת POST לא ודאית נבדקת באמצעות מזהה החשבון; אין POST נוסף כאשר קיים ספק.
- טיוטה קיימת משמשת לניסיון חוזר. שינוי נמענים מתוקן במקום, בלי יצירת הודעה נוספת.
- משתמש אחר בדשבורד אינו יכול להשלים דואר של המפיק המקורי, גם אם הועבר טוקן מתאים.
- חשבון Microsoft שונה אינו מתקבל אפילו אם יש לו גישה משותפת לתיבת המפיק.
- כשל בדואר אינו מבטל חשבון, משחרר חיוב, מייצר PDF מחדש או מוחק מסמך SharePoint.
- הסטטוסים: טיוטה מוכנה, ממתין לחיבור Microsoft, חוסר נמען, שגיאה או תוצאה הדורשת בדיקה.
  חיבור לחשבון Microsoft הנכון מאפשר המשך אוטומטי; כפתור חיבור אינו כפתור להעברת חשבונות.

## השלמה לאחר חיבור מחדש

`finance-invoice-mail.js` פועל במעטפת הדשבורד עבור משתמש בעל הרשאת כספים.
הוא בודק עבודות השייכות למשתמש בלבד בעת כניסה, חזרת פוקוס, חיבור Microsoft ובמרווח של דקה.
הבדיקה אינה פותחת חלון התחברות אוטומטי. ללא טוקן זמין אין בקשת יצירת טיוטה.
כל שרשרת בודקת מחדש את זהות המשתמש כדי לעצור אם התחלף משתמש באמצע.

`finance_pending_delegated_accounts` מחזיר עד 20 מזהי חשבון של המשתמש המקורי,
בכפוף למועד ניסיון חוזר ולתקרת עשרה ניסיונות. חיבור מחדש משחרר מיד עבודות שממתינות לחיבור
או שנחסמו עקב חשבון Microsoft שגוי. תוצאה לא ודאית ממשיכה לדרוש בירור הודעה לפני POST.
משימות עם כשלים חוזרים נעצרות ומוצגות לטיפול, ולא מתבצעת לולאת יצירה בלתי מוגבלת.

ללא דפדפן פתוח לא מתבצעת השלמת דואר. החשבון, ה־PDF ומצב העבודה נשמרים עד חזרת המפיק.
אין שמירת refresh token בשרת ואין ניסיון להחליף את הרשאת המשתמש בהרשאת Application.

## פריסה ובדיקות

יש להחיל את `20261103211803_finance_delegated_invoice_drafts.sql`, לפרוס את פונקציית ההפקה
עם JWT פעיל ולפרוס את הממשק. המיגרציה מסירה את cron בשם finance-outlook-drafts,
מנטרלת את פונקציית הפצת עבודות ה־Application ואת היכולות הישנות, ומוסיפה waiting_connection.
תור העבודות משמש למצב ולמניעת כפילויות בלבד; הוא אינו שומר הרשאות Microsoft.
אין שינוי בסודות SharePoint, ב־Auth או בהרשאות Microsoft של הארגון.

הבדיקות מכסות שמירת מסמך ללא חיבור, התאמת תיבות מאומתת, תיבה משותפת שגויה,
משתמש דשבורד אחר, חיבור מחדש, פקיעת טוקן, מרוץ ניסיונות, POST לא ודאי,
אימות ה־PDF המקורי, השבתת cron, קורסים וסדנאות ושמירת כללי גפ״ן.
בדיקה חיה חייבת להתבצע דרך הסשן של המפיק בדשבורד וב־Microsoft; חיבור Outlook אחר
או טיוטה שנוצרה באמצעות כלי חיצוני אינם הוכחה לבדיקת המסלול הזה.

מקור לבדיקת התיבה: [Microsoft Graph mailFolder](https://learn.microsoft.com/en-us/graph/api/mailfolder-get?view=graph-rest-1.0).
