## בדיקות קריאה לאחר התקנת המיגרציה

```sql
select p.oid::regprocedure, p.prosecdef,
       has_function_privilege('authenticated',p.oid,'execute') as authenticated_execute,
       has_function_privilege('anon',p.oid,'execute') as anon_execute,
       p.proconfig
from pg_proc p
where p.oid=to_regprocedure('public.av2_save_historical_travel_batch(bigint,date,jsonb)');
select column_name,
       has_column_privilege('authenticated','public.users',column_name,'select') as can_read
from (values ('auth_user_id'),('emp_id'),('is_active'),('role')) c(column_name);
```

תוצאה נדרשת: שורה אחת לפונקציה, prosecdef=false, authenticated_execute=true, anon_execute=false וכל ארבע הרשאות העמודות true. בדיקות אלה אינן מחליפות smoke בהרשאות מדריך.

## חזרה לאחור

- תנאי עצירה: שגיאות הרשאה בלתי צפויות, פגיעה בשלמות נתונים, כתיבות כפולות, שמירה חלקית או תקיעות שאינן מתאוששות. לעצור את ההפצה ולהימנע מניסיונות כתיבה אוטומטיים.
- אם המיגרציה נכשלה לפני פריסת הממשק: לא לפרוס את הממשק. לבטל את טרנזקציית המיגרציה ולבדוק את השגיאה; הממשק הקיים ממשיך לעבוד ללא ה־RPC החדש.
- אם הממשק כבר נפרס: **להחזיר תחילה את קוד הממשק לארטיפקט/קוד הייצור ששומר**, עם מספרי cache וסמן rollback חדשים הגבוהים מהגרסה שנכשלה. לא להחזיר רק קובצי cache ישנים. לאמת הורדת נכסים ומסלול נוכחות בסיסי בלקוח חדש וב־PWA קיימת.
- **להשאיר את ה־RPC החדש מותקן כברירת מחדל**, כדי שלשוניות/PWA שעדיין מריצות את הממשק החדש לא יישברו. אין למחוק פונקציה לפני שלקוחות שתלויים בה הוחלפו. הסרה עתידית, אם תידרש, היא פעולת תחזוקה נפרדת לאחר בדיקת תלות ואישור.
- לא לשחזר גיבוי טבלאות באופן גורף: הוא עלול למחוק דיווחים תקינים שנוספו מאז הפריסה. לשמור נתונים ואודיט, ולתקן נתון מזוהה רק לאחר בירור ואישור. שתי המיגרציות אינן דורשות rollback של נתוני עבודה. במקרה של תקלה ייחודית ב־RPC הקבלות ניתן לשחזר את הגדרתו והרשאותיו מהעותק שנשמר, לאחר החזרת הקליינט ובדיקת התלות; אין למחוק קבצים או שיוכים תקינים.
