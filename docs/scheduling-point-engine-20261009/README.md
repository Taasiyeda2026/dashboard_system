## סיבות ותיקונים

- **עלויות חוזרות:** יצירת תרחישים סרקה שוב מפגשים וחישבה תאריכי שחרור בכל שעה; שלב הסיום בנה מחדש את תפוסת כל השורות שכבר התקבלו לכל שורה נוספת. נוספו אינדקס ימי שבוע מקומי, חישוב יחיד של תאריכי השחרור, מטמון מוגבל לפענוח שעה/יום בלבד, ואינדקס תפוסה מצטבר. אין מטמון גלובלי של זמינות, הרשאות או הקשר עסקי.
- **הקשר אופטימיזציה:** במקום לבנות מחדש את כל ההקשר, האופטימיזציה מעתיקה את הקשר הריצה ומשנה את האינדקס של המדריך המושפע; אינדקסים סטטיים נשמרים.
- **תלויות:** הרחבה טרנזיטיבית מחברת עמיתים באותו בית ספר ומדריכים/חלופות/מחליפים בתאריכים משותפים. היעדר טביעת תאריכים מחייב הרחבה שמרנית. תאריך משותף ללא משאב משותף אינו תלות. נעילות, שיבוצים קיימים ותאריכים מעוגנים נשארים עוגנים. נשמרו סימוני invalidation השמרניים הקיימים בשרת; לא נטען שכל שינוי תמיד מצריך פעילות אחת בלבד.
- **זמן מעבר:** סינון הבחירות בין קבוצות בתי ספר בדק חפיפות בלבד, בעוד האימות הסופי בדק גם נסיעה. הסינון משתמש עכשיו באותה מדיניות מרחק, זמן ובאפר, מול הפעילות הקודמת והבאה, עם כתובות המקור. מועמד עם מסלול לא ידוע אינו מתקבל. תוקנה גם אי־התאמה ב־`peek` למסלול מכתובת לעצמה: אפס דקות כפי שמסלול החישוב כבר הגדיר; כתובות שונות עם מסלול חסר נשארות לא ידועות.
- **תאריך רשמי:** מסלול fixed-proposal אפשר התאמת תאריך בתגובה לחסימת מדריך. במסלול זה נאסרה הזזת תאריך ונוסף guard באימות הסופי. פעילות ללא מדריך מתאים נשארת בלתי משובצת בתאריך הרשמי.
- **כישלון אופטימיזציה:** נשמר עותק בסיס שעבר אימות קשיח לפני שיפור נוסף. שגיאת אופטימיזציה, חריגת תקציב או תוצאה לא תקינה מחזירות אותו עם סימון מפורש של שיפור שלא הושלם. ביטול, אובדן בעלות, שגיאות הרשאה וגרסה אינם הופכים להצלחה. התראה נשמרת גם לאחר טעינה חוזרת.
- **גרסה ישנה:** תכנון שמור מוצג ללא הפעלת מנוע, אבל מסומן כממתין לאימות אם עידן האימות השתנה. בקשת עדכון מפורשת במסלול marker-only מבצעת אימות לפני שינוי הסמן; כשל או נסיעה לא מאומתת אינם מאפשרים אישור גרסה. סטייה מוכחת בתאריך קבוע בלבד יוצרת יעד תיקון נקודתי.

## תקינות וראיות

בכל המדידות המתוקנות: אפס כשלי אימות ואפס אזהרות נסיעה. בבסיס הישן, בתכנון של 253 שורות, היו 736 אזהרות `travel_unverified` עקב כתובות זהות ללא ערך במטמון הסינכרוני; אלה נפתרו בלי להקטין כיסוי. בסיס 25 הפעילויות הישן נכשל בשמונה מעברים ללא מרווח מספק; בסיס התכנון המתוקן תקין בכל שלוש הריצות.

שעות שיבוץ בפועל נשמרו: 1,012 שעות בתוכנית המלאה והנקודתית, 100 בקבוצת 25, ו־20 בקבוצת 5. מרחק כולל וציון תפעולי נשארו זהים בהשוואות התקינות: נקודתי 2,065 ק״מ / 71.9; ארצי 2,070 ק״מ / 71.8; בית ספר 50 ק״מ / 68.5. אין כאן טענה להגדלת ניצול השעות או לחישוב אחוז ניצול מכל קיבולת השנה.

השוואה לתכנון השמור אישרה שאין שינוי בתאריכים, בשעות או במדריך הראשי של 252 הפעילויות שלא חושבו. חלק משדות הנרמול, כגון `planningLocked: false` במקום שדה חסר, נוצרים גם במסלול הקיים; אלה אינם שינוי שיבוץ. ה־fixture במסד נשאר ללא כתיבה.

**73 בדיקות עברו, 0 נכשלו** בסבב הסיום, מתוך שבעה קבצים ממוקדים. הלוג כולל שמות ומספר מקרים שבוצעו בפועל: [acceptance-tests.log](acceptance-tests.log). נבדקו מעבר חוקי/לא חוקי וכיוון נסיעה, גבולות מרחק ובאפר, מסלול חסר, תלויות עקיפות ונתונים קומפקטיים, מדריך לא מתאים או חסום, תאריך רשמי, חלופה תקינה, עוגנים, בסיס לאחר כשל אופטימיזציה, ביטול ואובדן בעלות, checkpoint פגום, חידוש/rebase, שימוש חוזר בהקשר, two-phase commit ועידן אימות, ו־PWA.

בדיקת DOM מפעילה בפועל חיפוש, דפדוף, פתיחת קורס וחזרה למסך עם 253 פעילויות שמורות: `activitiesComputed=0`, `contextRebuilds=0`, `scheduleCalls=0`, ללא בקשות כתיבה. שלוש בקשות קריאת מצב אישור נעשו ל־`course_assignment_manager_approval_state`; זהו RPC קריאה למרות שיטת HTTP POST. הרשת בחסימה במבחן, ולכן זו הוכחת אי־הפעלת חישוב/כתיבה, ולא בדיקת Auth/שרת חיה.

`npm run build` עבר, 9.57 שניות; נותרה אזהרת גודל chunks קיימת. [build.log](build.log). HOTFIX_VERSION קיבל סמן חדש ו־frontend CACHE_VERSION הועלה ל־1979. בדיקות חזרו כאשר קוד רלוונטי השתנה; מדידה שחפפה לבנייה הושלכה ונמדדה מחדש. לא הורצה חבילת legacy מלאה או נוספה תשתית CI כבדה.

## מגבלות והמלצה

מומלץ להעביר את ה־PR לביקורת קוד. התיקונים הוכיחו שיפור ותקינות בסביבה המבודדת; מיזוג או פריסה מחייבים את אישור המשתמש. אין צורך ב־migration.

הריצה הארצית עדיין ארוכה וצורכת כ־1.1 GiB; Web Worker/שירות שרת נשארים לשלב הבא. לא הוכחה כאן תגובה מיידית בכל מכשיר: לא בוצעו בדיקות דפדפן חלש או מובייל פיזי, בדיקת עומס משתמשי Supabase, אימות שרת חדש או שמירה דרך RPC חיה. מדידות המנוע אינן מדידות UX. תהליכי שמירה קיימים מוגנים בבדיקות הרגרסיה; אין טענה שבוצעה כתיבת קבלה לסביבת ייצור. אילוץ גלובלי או טביעת תלות חסרה יכולים עדיין להצדיק היקף רחב, ויש למדוד בנפרד נתוני אמת שעברו אנונימיזציה לפני קביעת SLA.

## שחזור ידני מבודד

ה־fixture המצורף הוא סינתטי בלבד, gzip בקידוד base64. SHA256 של קובץ ה־JSON המפוענח: `b1c075c4e6c56017324f3e9f622856012fc9c00917d6439a0b2bd9aaf90d37e1`.

1. לפענח את `synthetic-fixture.json.gz.b64` לקובץ JSON זמני ולבדוק את הגיבוב.
2. במכולת PostgreSQL 17 זמנית ללא volume, עם פורט הקשור ל־127.0.0.1 בלבד, ליצור `isolated_fixture(id text primary key,payload jsonb not null)` ולהכניס שורה `synthetic-253` עם ה־JSON באמצעות פרמטרים. לא להשתמש במסד קיים.
3. להריץ מהשורש, עם Node ו־`pg` מהתלויות המקומיות:

```sh
BENCH_DATABASE_URL=postgres://postgres@127.0.0.1:55442/postgres \
BENCH_CASE=point BENCH_ITERATIONS=7 RESULT_FILE=/tmp/point-results.json \
node --expose-gc scripts/benchmarks/scheduling-point-engine-acceptance.mjs
```

להוסיף `BASE_ONLY=1` לבסיס בלבד; `BENCH_CASE=school5`, `cohorts25`, `national` לשאר התרחישים (3, 3, 1 דגימות בהתאמה). `ENGINE_ROOT=/absolute/path/to/baseline` מפנה לעותק בסיס. הסקריפט קורא SQL אחד, אינו כותב למסד וחוסם רשת למסלולים/חישוב. לצורך פירוק שלבי הבסיס יש להוסיף לשם את אותם טיימרים בלבד; מדידת זמן כולל אינה מחייבת זאת. להריץ גרסאות ברצף, ללא build או בדיקות במקביל, ולמחוק את המכולה הזמנית בסיום.

```sh
node --test --test-isolation=none tests/scheduling-point-navigation.test.mjs tests/scheduling-point-engine-acceptance.test.mjs tests/scheduling-prepared-context-reuse.test.mjs tests/course-scheduling-planning-self-invalidation.test.mjs tests/course-scheduling-two-phase-commit.test.mjs tests/course-scheduling-checkpoint-resume-rebase.test.mjs tests/service-worker-pwa-cache.test.mjs
```
