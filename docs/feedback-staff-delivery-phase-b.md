# שלב ב׳ — משובים אוטומטיים לצוות החינוכי, כבוי כברירת מחדל

המשך ישיר ל־PR #2301: משתמש ב־`feedback_staff_auto_candidates` וב־`feedback_staff_auto_outbox` הקיימים. אין רשימת קורסים נוספת ואין שינוי ב־RPC של תלמידים או מדריכים.

## מה נוסף

- הכנת תור ב־05:00 ותפיסה אטומית ב־08:00 לפי `Asia/Jerusalem`; שתי שכבות חסימה: `FEEDBACK_STAFF_DELIVERY_ENABLED` ובמסד `feedback_staff_auto_control.enabled` עם `activation_at` חובה.
- בדיקה חוזרת של הקבוצה המאוחדת, כל חבריה, הפעילות המייצגת, מועד הסף ואיש הקשר. בדיקה נוספת סמוך לקריאת Graph בודקת גם שקישור הנמען לא הוחלף.
- מקור נמען יחיד: `activities.school_contact_id → contacts_schools.id → contacts_schools.email`.
- שימוש בתבניות המפורסמות `educational_staff/pre` ו־`educational_staff/final` וב־`feedback_recipients.token`. קישור ישן של איש קשר אחר מוחלף רק אם אין תשובות; קמפיין שהושלם/נסגר/פג אינו נפתח מחדש אוטומטית.
- שליחת נוסח עברי קצר עם תוכנית, בית ספר, שלב וקישור אישי באמצעות אותה תשתית Microsoft Graph וארבעת משתני `MS_*` הקיימים. הודעות נשמרות ב־Sent Items לצורך בירור עתידי.
- טבלת ניסיונות, מזהה claim ייחודי ונעילות במסד. ייחוד `(group_key,stage)` ובדיקת חפיפת החברים ההיסטוריים חוסמים שליחה כפולה גם לאחר החלפת נציג, שינוי שם או איחוד/פיצול קבוצה.
- `accepted` רק לאחר HTTP 202. תגובות דחייה מפורשות מסומנות `failed`; timeout, אובדן תשובה או HTTP 5xx מסומנים `unknown`. לא מתבצע retry אוטומטי של failed או unknown. קריסת worker אחרי תחילת Graph מסומנת unknown; לפני Graph — failed.
- סטטוס קומפקטי בשתי עמודות המשובים בלשונית הצוות בלבד: טרם הגיע מועד / ממתין לשליחה / נשלח / נכשל / דורש טיפול. RPC הסטטוס מוגן באותו `feedback_can_view` ומחזיר רק מזהה פעילות, שלב, מצב וסיבה; אין מיילים או tokens בתשובה.

שינוי מקור בין הכנה לשליחה מבטל את הפריט לאותו בוקר. הכנת היום הבא יכולה לעדכן פריט cancelled לפי נתוני האמת; accepted/unknown אינם מתאפסים. Failed ו־needs_attention נשארים לבירור מפורש. אין מסך retry חדש ואין הרשאות משתמשים נוספות.

## בדיקות

פקודות מיועדות לנתוני בדיקה בלבד. בדיקת PostgreSQL מסרבת ל־URL שאינו localhost/127.0.0.1 ומאפסה את הסכמות במסד הזמני.

```sh
node --test tests/feedback-staff-automation-dryrun.test.mjs tests/feedback-staff-delivery.test.mjs
STAFF_DELIVERY_TEST_DATABASE_URL=postgresql://postgres:local-test@127.0.0.1:55432/feedback_test node --test tests/feedback-staff-delivery-postgres.test.mjs
```

בדיקת UI ידנית בלבד, אינה מחוברת ל־CI: שרת Vite מקומי עם `VITE_SUPABASE_URL=http://127.0.0.1:59999`, ולאחריו `node e2e/impact-feedback/staff-delivery-ui.e2e.mjs`. כל קריאות ה־API מדומות, ותעבורה לא־מקומית נחסמת. נבדקו 1440px ו־390px, שתי מחציות, כל התוויות, כשל קריאת סטטוס והיעדר תגיות מייל לתלמידים ולמדריכים.

תוצאות: 5 בדיקות שלב א׳, 7 בדיקות delivery ו־11 תרחישי PostgreSQL עברו ללא דילוגים; שתי בדיקות הדפדפן עברו. נבדקו גם ארבעת קובצי domain/UI/cache/PWA הקיימים ו־Build. ה־Build דרש התקנת התלויות מה־lockfile בגלל qrcode חסר בסביבה; ניסיון שני עבר. בדיקת המסד הורצה מחדש רק בעקבות שינוי בדיקה/קוד: שרשרת תבניות חסרה תוקנה בסביבת הבדיקה; בהמשך נוספו בדיקת token ותרחישי רגרסיה.

בדיקה ותיקה נפרדת `impact-feedback-postgres.test.mjs`: תרחיש אחד עבר ואחד נכשל בציפיית סיום מחצית של מדריך (`2027-02-15` מול `2027-03-01`). אותה בדיקה בונה רק את שרשרת המיגרציות הישנה, ללא מיגרציית שלב ב׳; לא שונה מנגנון המדריכים כדי לתקן ציפייה זו. בדיקת התלמידים והמדריכים החדשה לאחר מיגרציית שלב ב׳ עברה.

## מצב הייצור בזמן העבודה

- לא הוחלה מיגרציית שלב ב׳ על Supabase ולא נפרסה הפונקציה.
- בקריאת הייצור התור של שלב א׳ היה ריק; לא היו Jobs בשם `feedback-staff%`.
- **לא נשלחו מיילים אמיתיים.** בדיקות Graph השתמשו ב־Response מזויף או בחריגת תקשורת מזויפת.
- שני תהליכי Cron מוכנים באמצעות `feedback_staff_auto_install_inactive_cron()`; המיגרציה לא קוראת לה. גם הפעלה ידנית שלה מתקינה Jobs במצב inactive בלבד, בתוך אותה טרנזקציה.
- המיגרציה נוצרה עם Supabase CLI; חותמת הזמן הוזזה לאחר מיגרציית שלב א׳ כדי לשמור על סדר התלויות.

## מה נשאר להפעלה עתידית — רק לאחר אישור מפורש נוסף

1. למזג את PR של שלב ב׳ ולהחיל את המיגרציה כשהשליחה כבויה. לפרוס `feedback-staff-automation` עם `FEEDBACK_STAFF_DELIVERY_ENABLED=false`; Endpoint ללא user JWT מוגן בסוד השרת הקיים `FEEDBACK_STAFF_DRY_RUN_SECRET`.
2. לוודא את משתני `MS_TENANT_ID`, `MS_CLIENT_ID`, `MS_CLIENT_SECRET`, `MS_MAIL_SENDER` הקיימים והרשאת `Mail.Send` לתיבה המיועדת. בדיקות אלה לא שולחות מייל. להגדיר `FEEDBACK_STAFF_BASE_URL` לכתובת הייצור של המשוב.
3. לשמור ב־Vault את אותו סוד בשם `feedback_staff_automation_secret` ולהתקין את שני ה־Jobs הלא־פעילים באמצעות הפונקציה המיועדת לבעל המסד בלבד. נדרש secret חזק; אין להדפיסו או לשמור אותו ב־Git.
4. לאשר מועד הפעלה עתידי מדויק, ולרשום `activation_at` בהתאם. הזכאות המקורית חייבת להיות אחרי הסף גם בהכנה וגם בבדיקת השליחה; לא יוצרים משלוחים על מפגשים שקדמו לסף.
5. רק לאחר אישור הפעלה: להדליק את דגל המסד ודגל ה־Edge, ולהפעיל את שני ה־Jobs. Cron פועל שעתית ב־UTC, אך קורא לפונקציה רק בשעה 05/08 בישראל; אין שינוי ב־cron.timezone של Jobs אחרים.
6. לבדוק את ספירות התור וניסיונות הבוקר הראשון. `accepted` פירושו Microsoft Graph קיבל את ההודעה, לא אישור מסירה לתיבת הנמען. כל `unknown` דורש בירור ב־Microsoft 365 לפני החלטת פעולה; אסור לאפסו ולשלוח שוב אוטומטית.

השליחה מטפלת בתור עד 1000 פריטים להפעלה, וכל פריט נבדק שוב במסד בזמן השליחה. אם יש backlog עקב תקלה/מגבלת זמן, הוא נשאר בתור; אין retry עיוור של פריטים שכבר התחילו משלוח.
