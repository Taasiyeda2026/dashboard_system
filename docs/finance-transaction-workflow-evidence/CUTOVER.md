# אימות סופי ותוכנית פריסה לחשבונות עסקה

בסיס הרגרסיה הוא `origin/main` בנקודה `a4dc351b`. האימות המקומי משתמש ב־PostgreSQL 17 ב־loopback ובחשבונות סינתטיים. בבדיקת קריאה בפרויקט Dashboard נצפו 35 חשבונות, 141 שורות חיוב, 6 תקבולים ו־47 הקצאות. לכל חשבון שהופק היה מספר. לא הועתקו נתוני החשבונות ל־staging.

בדיקת המיגרציות משווה חשבון שהופק, הפניה ל־PDF, תקבול, הקצאה ויתרה לפני ואחרי כל שש המיגרציות. בדיקת המחיקה מוודאת שהחשבון יורד גם מתוצאת RPC היתרות, תוך שימור התקבול ושחרור ההקצאה.

## תנאי אישור

- נדרש יעד Supabase מבודד עם משתמש כספים ועם אדמין, תיקיית SharePoint ייעודית, תיבת Outlook לבדיקה והרשאת Graph של האפליקציה לתיקייה. בדיקת פרויקט Dashboard העלתה רק את ענף ברירת המחדל, ובחיפושים ב־Microsoft לא זוהו תיבה ותיקייה ייעודיות.
- ביעד שאינו פרויקט הייצור, Edge דורשת `FINANCE_TEST_MODE=true`, מזהי `FINANCE_TEST_DRIVE_ID` ו־`FINANCE_TEST_FOLDER_ID`, ואת כתובת `FINANCE_TEST_MAILBOX`. התיבה חייבת להיות תיבת המפיק המקורי וגם הנמען היחיד בטיוטה. לפעולות ההעלאה נדרשים פרטי האפליקציה שהוקצתה לתיקיית הבדיקה. הפונקציה דוחה את תיקיית הייצור במצב בדיקה. בפרויקט הייצור נשאר יעד SharePoint הקיים.
- לאחר הרצת שש המיגרציות ב־staging, להפיק מחשבון סינתטי, להשוות PDF וסכום ולבדוק בתיבה שנוצרה טיוטה אחת. לתקן במקום, להשוות מספר, מזהה וגרסאות, למחוק כאדמין ולאמת מחיקת ה־PDF הפעיל ושחרור חיוב והקצאות. להפיק שנית ולבדוק שימוש חוזר במספר האחרון. לבדוק גם ניסיון חוזר לאחר שגיאת רשת, ומחיקה בזמן הפקה פעילה. לתעד מזהי בדיקה וזמנים. אין צורך בשליחת דואר בתרחיש.
- לפני מיזוג, לאשר גם תוצאות staging מול עותק נתונים מייצג ומאושר לשימוש, התואם לשיעורי מימון ולסטטוסים ההיסטוריים. בדיקת PostgreSQL המקומית משתמשת בנתוני דוגמה.

## חלון הפריסה לאחר אישור

1. לקבוע חלון תחזוקה ולהשעות פעולות כתיבה בחשבונות עסקה. לוודא שמנגנון אוטומטי לפריסת Edge או GitHub Pages לא יקדים את סדר הפריסה בעת מיזוג. לבדוק שאין הפקות, תיקונים או מחיקות פעילות או פעולות אחסון שממתינות לבירור.
2. ליצור נקודת שחזור מאומתת ולשמור את SHA הייצור, גרסת Edge, מונה המספור וערך ה־Sequence, וכן מדדי בסיס וקובץ אימות פנימי של סכומים, תקבולים, הקצאות ויתרות. לבצע את ההשוואה בסדר יציב לפי מזהה, ללא ייצוא נתונים לדוח.
3. להחיל את שש המיגרציות בסדר שמותיהן. לוודא לפני שחרור שהמדדים והטביעות ההיסטוריות תואמים, שהמונה מתחיל מעל הקיים ושכל הרשאות ה־RPC ו־RLS תואמות להרשאות הכספים.
4. להעלות את Edge מאותו SHA ואז את הממשק עם שני סמני המטמון. לבצע קריאות אימות ללא כתיבה מול ייצור. מסלול הכתיבה המלא נבדק ב־staging.
5. לשחרר את ההשהיה ולבדוק את תוצאות ההפקות העסקיות הבאות לפי יומני Edge, SharePoint ו־Outlook. לעקוב אחר העלאות במצב לא ודאי, מחיקות ממתינות ושגיאות מספור.

## התאוששות

- אם האימות נכשל לפני שחודשו פעולות הכתיבה, להשאיר את המסך בהשהיה. לתקן או לחזור לגרסאות Edge והממשק שנשמרו רק באמצעות תהליך מתואם עם שחזור DB או מיגרציית התאמה.
- אם כבר בוצעו פעולות עסקיות בגרסה החדשה, להעדיף תיקון קדימה. לפני שחזור לתאם עם כספים את רשימת החשבונות, התקבולים וקובצי Microsoft שנוצרו אחרי נקודת השחזור. לשמור את יומן המחיקות והגרסאות וליישב פעולות לפי מזהה פנימי. שחזור בסיס הנתונים אינו מחזיר קובץ שכבר הוסר משירות חיצוני.
- אם חוזרים להקצאת Sequence, לסנכרן אותה תחת נעילה לערך שאינו נמוך מהמונה החדש או מהמספר הפעיל המרבי ועוד אחד. לא לפתוח כתיבה עד אימות אי־התנגשות בין הגרסאות.
