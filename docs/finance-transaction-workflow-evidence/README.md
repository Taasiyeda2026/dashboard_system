# מסירת שדרוג חשבונות העסקה

[PR #2808 בטיוטה](https://github.com/Taasiyeda2026/dashboard_system/pull/2808) בענף `feat/finance-transaction-account-workflow`. בסיס השינוי הוא `main` בנקודה `a4dc351b`. בדיקות מול פרויקט Dashboard הפעיל היו בקריאה בלבד. תרחישי הכתיבה רצו ב־PostgreSQL 17 מקומי, ופעולות Microsoft השתמשו בשירותים מדומים.

## שינויים

- הזכאות מציגה חסימת נמען מאותו פתרון כתובות המשמש את ההפקה. שריון ראשוני נשמר ללא מספר. מספר משוריין אחרי בדיקת זכאות, נמען ונעילת הפקה, ומשויך למסמך הסופי בעת קיבוע ההפקה.
- טיוטות מסך ההפקה הידנית נשמרות עם גרסה, ניתנות לפתיחה מחדש ועוברות דרך אימות זכאות ותצוגה מקדימה לפני הפקה. הטיוטה זמינה לבעליה ולאדמין. מחיקה זמינה לאדמין.
- מספור בפורמט הקיים משתמש במונה טרנזקציוני. מחיקת המספר האחרון מחזירה אותו למונה רק לאחר השלמת המחיקה. מספרים פנויים באמצע הרצף נשארים פנויים. שם האחסון ב־SharePoint כולל מזהה פנימי כדי למנוע התנגשות עם PDF היסטורי של מספר שהוחזר לשימוש.
- PDF של מממן שאינו גפ״ן מרכז לפי פעילות ומממן ומציג את בתי הספר והסכום בפועל. בחיוב חלקי מופיע סימון חיוב חלקי במקום מחיר יחידה שהכפלתו בכמות הייתה יוצרת סכום שגוי. מחירים שונים לאותה פעילות אצל אותו מממן עוצרים את ההפקה ומוצגים לבירור. שורות החיוב הפרטניות וקבוצות גפ״ן נשמרות.
- תיקון שומר את מזהה החשבון ואת המספר, מוסיף גרסה ומתעד מבצע וזמן. תאריכי מסמך נשארים מוגבלים לאדמין. סכום מתחת להקצאת תקבולים קיימת חסום לבירור בשרת.
- מחיקת אדמין משתמשת ביומן עם מזהה פנימי וממתינה למחיקת ה־PDF הפעיל מ־SharePoint. החשבון מוסתר ומפסיק להשתתף בגבייה, והקצאות התקבולים משוחררות. ה־PDF של גרסאות קודמות וטיוטות Outlook קיימות נשמרים.
- לאחר תשובת שמירה לא ודאית, החשבון נשאר ניתן להשלמה בהיסטוריה. ניסיון חוזר משתמש באותו שריון, אותו מספר וחתימת PDF תואמת. אם החתימה או נתוני הזכאות השתנו אחרי כתיבה לא ודאית, החשבון נעצר לבירור כדי להימנע מדריסה או מחיוב כפול.
- ההיסטוריה כוללת חיפוש מספר, בית ספר ומממן, סינון חודש וסטטוס ותצוגה בלבד לבעלי הרשאת מעקב גבייה.

קובצי המימוש נמצאים ב־`frontend/src/api.js`, במסכי הכספים תחת `frontend/src/screens/`, ובשני קובצי `supabase/functions/finance-transaction-accounts/`. עדכוני המטמון נמצאים ב־`frontend/src/config.js` וב־`frontend/sw.js`. שש המיגרציות מתחילות ב־`20261126131805` ומסתיימות ב־`20261126133511`.

## מדידות

| מסלול | לפני | אחרי | תנאי המדידה |
|---|---:|---:|---|
| חישוב זכאות | 626.5 ms | 486.3 ms | חציון ב־175 פעילויות סינתטיות ו־350 שורות חיוב. 5 מדידות לאחר חימום. 1 RPC בכל מדידה |
| PDF בתצוגה מקדימה | 339.2 ms | 398.2 ms | חציון מקומי, 5 מדידות ו־2 קריאות RPC, כולל גופן ועיבוד PDF |
| הפקה עד טיוטת Outlook | 406.9 ms | 399.1 ms | חציון מקומי, 5 מדידות. 10 RPC ו־8 קריאות Graph מדומות בשתי הגרסאות |

במדדים המצטברים של Supabase הפעיל נמדדו 598 קריאות זכאות, ממוצע 1,193 ms ומקסימום 5,647 ms. זהו קו בסיס מצטבר בלבד. זמני רשת אמיתיים ב־Microsoft, מסך ראשון מקצה לקצה וזמני חיפוש ושמירת טיוטות בסביבת staging משותפת טרם נמדדו. בדיקת Chromium שימשה לבדיקת תצוגה עם נתונים סינתטיים.

## סדר פריסה והתאוששות

לאחר אישור, להריץ את שש המיגרציות ואת תרחישי ה־Microsoft בסביבת staging עם תיקייה ותיבה ייעודיות. לפני מעבר לייצור יש לוודא שאין הפקות, תיקונים או מחיקות פעילות ושניתן להשעות זמנית את פעולות הכתיבה במסך חשבונות העסקה. גרסת Edge הקודמת סומכת על מספר שניתן בעת השריון, ולכן נדרשת החלפה מתואמת של בסיס הנתונים, הפונקציה והממשק. לשמור נקודת שחזור ולתעד מראש את מונה המספרים ואת הספרות הגבוהות ביותר בשימוש.

במקרה כשל לאחר מעבר, להשעות כתיבה ולבדוק את יומן המחיקות, מצבי ההפקה, מונה המספרים והגרסאות לפני חידוש העבודה. החזרת קוד לבדה עלולה להחזיר הקצאת מספר דרך ה־Sequence. לפני חזרה לשיטה הקודמת יש לבצע מיגרציית התאמה מאושרת שמסנכרנת את ה־Sequence מול המונה ומספרי החשבונות בפועל. פעולות שכבר הושלמו ב־SharePoint וב־Outlook נבדקות לפי המזהים השמורים.
